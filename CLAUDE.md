# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Toon Studio (formerly Comic Translate; the code, package and class names still say ComicTranslate) is a PySide6 (Qt) desktop GUI application that automatically translates comics/manga/manhwa/webtoons. The pipeline: detect speech bubbles & text → OCR → translate (LLM or traditional) → inpaint (clean) the original text → render translated text back onto the image. It also supports a browser extension and PSD/CBZ/PDF/EPUB import-export, but the desktop app (`comic.py`) is the primary surface developed here.

There is a test suite (`tests/`, pytest) and a linter (`ruff.toml`), both run by `.github/workflows/test.yml` on every push and pull request. They cover pure logic and Qt-free-ish widget behaviour; anything involving a model, a network call or how a page actually *looks* still has to be checked by running the app (see "Verification" below).

## Commands

Setup (uses `uv`, Python 3.12):
```bash
uv init --python 3.12
uv add -r requirements.txt --compile-bytecode
uv pip install onnxruntime-gpu   # optional, only if an NVIDIA GPU is available
uv pip install torch torchvision "transformers>=5"   # optional, enables the PaddleOCR-VL engine
```

Run the app:
```bash
uv run comic.py
```

Run the tests and the linter:
```bash
uv pip install -r requirements-dev.txt
pytest                  # conftest.py forces the offscreen Qt platform itself
ruff check .
```

Syntax/import check the whole tree, when you want something faster than the suite:
```bash
python -m compileall -q modules app pipeline
```

Regenerate UI translations (see "Localization" below — never call `lrelease` directly):
```bash
python scripts/build_translations.py --update --compile th   # rescan sources, then compile Thai
python scripts/build_translations.py --compile               # recompile every language
```

Build a distributable (PyInstaller, mirrors `.github/workflows/build-*.yml`):
```bash
pyinstaller --noconfirm --clean --name ToonStudio --add-data "resources:resources" comic.py   # Linux
pyinstaller --noconfirm --clean --windowed --name ToonStudio --icon resources/icons/icon.ico --add-data "resources;resources" comic.py   # Windows (PowerShell `;` separator)
```

Every **build** workflow is `workflow_dispatch` only — nothing builds automatically on push or PR; `test.yml` is the one exception and is deliberately the opposite, since a gate only matters if it runs unasked. `build-windows-full.yml` is the same Windows build plus the PyTorch stack (`--collect-all torch torchvision transformers`), which is what makes PaddleOCR-VL reachable in a frozen bundle; it is separate because torch takes the download from a few hundred megabytes to several gigabytes, and its final step asserts the three packages actually landed in `dist/` rather than trusting `--collect-all`.

### Verification

`tests/` is where anything worth keeping goes. `conftest.py` does two things before Qt loads: forces the offscreen platform, and repoints `XDG_DATA_HOME`/`XDG_CONFIG_HOME`/`HOME` at a temp directory — without that a run reads and writes the real user's glossaries, settings and models, since `modules/utils/paths.py` resolves them through those variables. A session-scoped `qapp` fixture supplies the one QApplication a process is allowed. A test that needs the full `ComicTranslate` window should build **one** per test (reload a project into the same window rather than opening a second): several per process make a native Qt font-database hang or segfault likelier in this environment, and closed windows' deferred deletions run inside later `processEvents()` calls, which can make anything debounced (the 400 ms text-edit timer) fire earlier than a test expects. `conftest.py` also runs `gc.collect()` after every test, on the GUI thread: Qt objects in Python reference cycles (an `ImageViewer` and its managers) are otherwise freed whenever the cyclic collector next runs, on whatever thread triggers it — and a QObject destroyed on a worker cannot stop the timers it started on the GUI thread, so one fires into freed memory at a later `processEvents()`. That was a real, gdb-traced SIGSEGV in `QTimerInfoList::activateTimers` (test_render_parity's viewers, destroyed from `_PyObject_ClearManagedDict` on a worker, crashing test_type_text_tool), and since it depends only on when collection runs, adding or removing any unrelated test moved it. The *hang* the suite also showed (about one full run in fifteen, always while a second window was being built) was a different bug with the same moral, and it lived in the app: `UpdateChecker` moved a Python QObject worker onto a `QThread` and destroyed it there with `deleteLater`. Destroying a Python-derived QObject calls into PySide, which needs the GIL, while Qt holds one of its 131 *pooled* signal/slot mutexes — and the GUI thread, holding the GIL, blocks on that same mutex whenever an object it is connecting hashes to it. Every window starts an update check, so one finishing while the next window was built froze the process (gdb: worker threads in `~QObject` → `Sbk_GetPyOverride` → GIL; main thread in `connectImpl` → `QBasicMutex::lockInternal`), and the app could freeze at startup the same way. The worker now runs on a plain Python thread that only emits `UpdateChecker`'s own signals. **Never move a Python-derived QObject to another thread and let it be destroyed there**; `tests/test_update_checker.py` guards the update checker against it. Whether older reports of a "font-database hang" were this is not proven, though they described the same moment.

`tests/test_psd_export.py` deliberately reads exported files back with **psd-tools** rather than PhotoshopAPI, which wrote them: asserting with the writer only proves it agrees with itself, and the first two PSD bugs found (a black merged-image section, and a frozen build dying before writing anything) were invisible that way. The third one, layers written as ZipPrediction so that every reader without Zip support saw an empty canvas, was invisible even to psd-tools — it decodes Zip perfectly well — so `test_layer_pixels_use_a_compression_every_reader_implements` reads the compression code out of the raw bytes instead. The fourth was invisible to psd-tools *and* to that: every layer written with **fill opacity 0** (`iOpa`), which draws nothing while document size, group and layer names, bounds, channel data and alpha all read as perfect — PhotoshopAPI's `fill` defaults to `0.0`. The rule underneath all four: PhotoshopAPI's defaults are chosen for Photoshop, and Photoshop is the one reader that never exercises them.

**After changing `psd_exporter.py`, open an export in a real editor.** `scripts/check_psd_in_photopea.py` drives Photopea in a headless Chromium and reports what it renders — the layer tree, each layer's own pixels (soloed, not inferred from the composite), whether a type layer is still editable, and the composite against the page ComicTranslate rendered. `tests/test_psd_in_photopea.py` runs it behind the `photopea` marker, deselected by default because it needs a browser and reaches a third-party site; `pytest -m photopea` runs it. Photoshop is deliberately not a dependency. Any layer that arrives hidden fails the check unless it is named with `--expect-hidden NAME`, for layers the user hid in the Layers panel (the export writes those as hidden layers on purpose). Soloing a layer changes visibility, so the harness restores each layer's *original* visibility before exporting the composite — restoring everything to visible once drew a user-hidden patch into the composite and blamed the export for it; `test_photopea_keeps_hidden_layers_hidden_and_honours_opacity` holds that. The site has to be reachable: an environment whose network policy blocks `www.photopea.com` (HTTP 403 from the proxy) cannot run it at all.

A PSD is **not** proven valid by the write succeeding, a non-zero file size, `PSD write finished` in the log, a PSD→PNG converter extracting an image, or psd-tools agreeing — the fill-opacity bug passed every one of those. Note that `app/controllers/psd_importer.py` is **not** an independent reader either: it imports `psapi` from `psd_exporter`, so reading our own export back only proves PhotoshopAPI agrees with itself. Photopea's script engine has three traps worth knowing before editing the harness — `return` inside `try` yields `undefined`, `x === undefined` is `false`, and reading a property off a length value kills the script with no reply — all documented at the top of `READ_TREE`.

**Type layers carry their own pixels, written after PhotoshopAPI is done.** PhotoshopAPI writes a type layer with bounds `(0,0,0,0)` and **no colour channels** — `TextLayer_8bit` has no parameter for pixel data (`width`/`height`/`pos_x`/`pos_y` only set a bbox, with *centre* semantics). Photoshop re-runs its text engine on open, so it never noticed; Photopea draws a type layer from its cached raster, so every page opened with the artwork and none of the translation, while still listing the layer and reading its string back. `psd_exporter._finish_type_layers` rewrites the layer section after `doc.write`: each type record gets the item rendered by `save_renderer.render_text_item_rgba` (the same `build_text_item` the flattened export uses, so the raster *is* what the app drew) as RLE channels, and stays a type layer — still editable, re-laid out from its text data once edited. Records are matched to text items by order (PhotoshopAPI writes bottom→top) and confirmed by the string in each TySh block; on any mismatch no raster is written rather than one on the wrong layer, and the rewrite is parsed back before it replaces the file. The same pass fixes a second defect: PhotoshopAPI declares TySh at its exact, sometimes **odd**, length and leaves the padding byte uncounted, which Photopea reads as the next block's signature ("Error in PSD file: wrong signature") — `_even_tagged_blocks` declares the padded length instead. Parity follows the content (EngineData writes numbers as text), which is why the test for it exports a spread of font sizes. That toast disappears within a second and Photopea still opens the file, so the harness installs a MutationObserver in Photopea's frame before opening and fails on any error message it shows. Editing the text in Photopea re-lays it out with Photopea's own fonts (it substitutes any it does not have) — the pixels match the app only until then. Photoshop itself is not verified. Two earlier suspects were ruled out by experiment, not argument: the empty EngineData containers written as `<<>>` and `[]` that psd-tools refuses to tokenise (byte-patching them to `<< >>`/`[ ]` left Photopea's composite bit-for-bit identical), and fill opacity (already 1.0).

**Exporting a text layer can kill the process rather than raise.** `_apply_editor_style` measures line height with `QFontMetricsF`, and Qt aborts when that is reached with no QApplication — no exception, no traceback, just SIGABRT and a 0-byte file, which is exactly what a user reports as "the app closed itself". Every PSD test used to pass `text_items_state: []`, so nothing in CI had ever written a text layer; `test_a_page_with_text_survives_the_write` and `test_the_text_layer_carries_the_string_it_was_given` close that gap, and both need the `qapp` fixture for the reason above.

psd-tools is a dev dependency and cannot replace PhotoshopAPI for export — it creates pixel layers and groups but has no way to author an editable text layer.

The linter is scoped to rules that catch bugs (`E9`, `F`, `B`) rather than style. Its first run found a live one: `drawing_manager.py` called two functions it never imported, inside a broad `except Exception`, so the Segment tool silently produced a plain rectangle instead of a fitted mask in webtoon mode. `ruff.toml`'s `ignore` list is a reviewed backlog, not a verdict — each entry says what it is and how many sites.

Some things the suite cannot reach. For changes to a `modules/*` engine that runs a model, the practical way to verify is still a standalone script run against a venv with the relevant deps installed (numpy/pillow/onnxruntime for detection/OCR/inpainting math; add pyside6-essentials only if the code path imports Qt). Importing `modules.utils` triggers `modules/utils/__init__.py` → `textblock.py` → `imkit`, which needs `mahotas`; importing anything under `app.ui` pulls in the full Qt stack. Prefer testing pure logic (e.g. `modules/utils/glossary.py`, `modules/rendering/render.py` wrap helpers, mask/box math) in isolation before wiring it into the Qt-dependent layers. For UI-affecting changes, actually launch `uv run comic.py` (or under `xvfb-run` in a headless environment) and exercise the feature — Qt widget wiring bugs do not show up in `compileall`.

## Architecture

### Layering

```
comic.py / controller.py (ComicTranslate, QMainWindow subclass)
  └─ app/ui/          Qt widgets: main window, canvas/graphics-scene editor, settings pages, dialogs
  └─ app/controllers/  Per-concern controllers the main window delegates to (image state, text editing,
                        projects/autosave, PSD import/export, manual workflow, batch report, shortcuts...)
  └─ pipeline/          Orchestrates modules/* into the end-to-end translate pipeline (see below)
       └─ modules/       Stateless-ish engines: detection, ocr, translation, inpainting, rendering, utils
```

`controller.py` defines `ComicTranslate(ComicTranslateUI)` — the QMainWindow. It owns `self.blk_list` (current page's `TextBlock`s), `self.image_files`, `self.image_states` (per-image dict: source/target lang, blk_list, viewer state, skip flag...), and instantiates `ComicTranslatePipeline` (`pipeline/main_pipeline.py`) which wires together the handler classes: `BlockDetectionHandler`, `OCRHandler`, `TranslationHandler`, `InpaintingHandler`, `SegmentationHandler`, `BatchProcessor`, `WebtoonBatchProcessor` — all sharing one `CacheManager`. `app/controllers/*` handle UI-adjacent concerns (text item editing, project save/load/autosave, PSD export, manual step-by-step workflow) and are attached to the main window as `self.xxx_ctrl`.

Two run modes share the same `modules/*` engines but have separate driving code: **Manual mode** (`app/controllers/manual_workflow.py` + the per-step buttons in `controller.py`: Detect → OCR → Translate → Segment → Clean → Render) and **Automatic/Batch mode** (`pipeline/batch_processor.py` for single images, `pipeline/webtoon_batch/` for long-strip webtoons which are chunked and stitched — see `chunk.py`/`flow.py`/`render.py`).

### Factory pattern for pluggable engines

Every pipeline stage that has multiple interchangeable implementations follows the same shape: an abstract base class, per-implementation subclasses, and a `Factory` class with a `create_engine(...)` classmethod plus an internal `_engines` cache keyed by a hash of the model/settings so switching engines mid-session doesn't require re-initializing unrelated ones.

- `modules/detection/factory.py` (`DetectionEngineFactory`) — `base.py` defines `DetectionEngine`; implementations include `rtdetr_v2_onnx.py`/`rtdetr_v2.py` (RT-DETR-v2, onnx/torch backends) and `bubble_seg_onnx.py` (YOLOv8-seg speech bubble detector, hybrid with RT-DETR text boxes).
- `modules/ocr/factory.py` (`OCRFactory`) — `base.py` defines `OCREngine`; implementations per-language/engine live in `manga_ocr/`, `pororo/`, `ppocr/`, plus API-based engines (`gpt_ocr.py`, `gemini_ocr.py`, `google_ocr.py`, `microsoft_ocr.py`, `easy_ocr.py`) and `user_ocr.py` for the hosted/managed backend. Two engines are **optional** — `easy_ocr.py` (needs `easyocr`) and `paddle_vl.py` (needs `torch`, `torchvision` and `transformers>=5`). They are always listed but greyed out when their packages are missing, with a tooltip naming the install command: `SettingsPageUI.__init__` records what is missing in `unavailable_ocr_engines` using `importlib.util.find_spec` (never by importing the engine, which would drag the model stack into building the settings dialog), `ToolsPage._mark_unavailable_ocr_engines` disables those rows, and `SettingsPage.load_settings` falls back to Default rather than restoring a saved engine this machine cannot run.
  `openrouter_ocr.py` is a `GPTOCR` subclass rather than its own engine: OpenRouter speaks the OpenAI chat-completions protocol, so only three things differ — the endpoint, `MAX_TOKENS_PARAM` (OpenAI renamed it to `max_completion_tokens`, OpenRouter kept `max_tokens`), and where the model id comes from. It reads the api_key already stored for the OpenRouter *translator*, so one balance covers both, and takes its model from a **separate `ocr_model` credential field** that falls back to the translator's `model` when blank — OCR runs a cheap vision model once per text block while translation runs a stronger one once per page, and one shared field means choosing for either silently chooses for both. That field is stripped *before* the fallback is chosen, since a field holding only spaces is truthy. It uses the id verbatim rather than through `MODEL_MAP` — a routing id like `google/gemini-2.5-flash-lite` is not one of this app's own model names. This is how a Gemini or GPT vision model is reached on OpenRouter credit without an account at the provider running it.
  `paddle_vl.py` is the odd one out architecturally: a 0.9B generative VLM that *writes out* what a crop says instead of decoding CTC logits, so it reads vertical CJK and stylised lettering with no special handling, at ~20s per block on a weak CPU. All 15 checkpoint files are sha256-pinned, and it loads through transformers' native `paddleocr_vl` support — passing `trust_remote_code=True` picks up the repo's own config class, which the built-in model class then rejects for a missing `text_config`.
- `modules/translation/factory.py` (`TranslationFactory`) — `base.py` defines `TranslationEngine`/`LLMTranslation`/`TraditionalTranslation`; `llm/base.py`'s `BaseLLMTranslation` is the shared LLM engine base (handles image encoding, system prompt via `PromptManager`, JSON-in/JSON-out translation contract). LLM engines (`llm/gpt.py`, `claude.py`, `gemini.py`, `deepseek.py`, `custom.py`, `openrouter.py`) subclass it; `openrouter.py` and `custom.py` both subclass `gpt.py`'s `GPTTranslation` since they're OpenAI-compatible APIs (note `GPTTranslation.MAX_TOKENS_PARAM` — OpenRouter needs `max_tokens` instead of `max_completion_tokens`). `deepl.py`, `microsoft.py`, `yandex.py` are non-LLM `TraditionalTranslation` engines. `user.py` (`UserTranslator`) is used instead of any of the above when the user is signed in to the managed/hosted account (checked via `app/account/auth/token_storage.get_token`).
- `modules/inpainting/` (`pipeline_config.py`'s `inpaint_map` dict, not a factory class) — `base.py` defines `InpaintModel`/`DiffusionInpaintModel`; implementations: `lama.py`, `aot.py`, `mi_gan.py`, and `smart_fill.py` (solid-fill cleaning: ranks progressively grown masks by border-colour uniformity and fills flat regions with the border's median colour, falling back to LaMa for non-uniform ones). The ranking itself lives in `mask_fitting.py`, ported from PanelCleaner.

`modules/inpainting/denoise.py` runs *after* whichever of those produced the cleaned page, at the one seam where patches get cut: `pipeline/inpainting.py`'s `_denoise_cleaned`, called by both `_get_regular_patches` (batch) and `get_inpainted_patches` (the manual Clean button, which also covers webtoon mode). It smooths a faded ring around the mask, because a low-quality JPEG carries ringing around every glyph and inpainting reconstructs the patch *from* those surroundings, leaving a halo where the text was. Structure follows PanelCleaner's denoiser (GPL attribution in the file header); the filter does not — PanelCleaner calls OpenCV's `fastNlMeansDenoising` and there is no OpenCV here, so it is a mahotas median instead.

Three things about it are load-bearing:

- **It works per mask region, not per page.** A page mask covers every bubble, so a single bounding box is very nearly the page — and a whole-page median costs 1.3s per page and 3s per webtoon strip, for a result that is then multiplied by a zero weight almost everywhere. `_mask_windows` cuts one padded window per region and merges overlapping ones (so a bubble's glyphs become one window, not forty). ~0.4s on a heavy page, and no longer scaling with page size.
- **Each window crops the *mask*, not the region.** A neighbouring bubble reaching into a window is denoised with it rather than clipped in half; windows are pairwise disjoint after merging, so nothing is written twice.
- **A region whose surroundings are a flat fill is skipped entirely**, bit for bit (`min_std`). This is what makes it safe to leave on by default: a clean PNG source loses nothing. `Settings > Tools > Tidy JPEG artefacts around cleaned text` turns it off, and a failure inside it is logged and swallowed — cleaning must not fail because tidying did.

### Text mask generation (what gets cleaned)

`modules/utils/image_utils.py`'s `build_block_mask_data` decides which pixels inside a detected box are lettering. Two sources, chosen by `Settings > Tools > Use the AI text segmentation model` and dispatched through `modules/utils/text_segmentation.py`:

- **Thresholding** (`modules/detection/utils/content.py`'s `detect_content_mask_in_bbox`) — Otsu plus connected-component filtering, per crop. Cheap and wrong whenever the lettering is not simply the darkest or lightest thing in the box.
- **Model** (default) — `modules/detection/text_seg_onnx.py` runs comic-text-detector's `seg` head over the whole page once (cached per page), and `modules/inpainting/text_mask_refine.py` uses that prediction to referee several candidate binarisations per box, keeping only components that improve agreement with it. This is the same algorithm PanelCleaner runs, ported to `imkit`; the file carries GPL-3.0 attribution.

Callers pass the page prediction down as `page_text_mask=` (see `pipeline/batch_processor.py`, `pipeline/webtoon_batch/chunk.py`, `pipeline/inpainting.py`). Interactive paths use `peek_page_mask()` instead, which returns the cached prediction or `None` and never runs inference — a brush stroke must not wait seconds for a model.

`imkit` is a partial `cv2` replacement and its semantics are not always OpenCV's; when porting cv2 code, check the specific function first (`erode`/`dilate` binarise their output, so grayscale morphology has to be reordered into a threshold plus binary morphology).

### Model downloads

All model weights are declared centrally in `modules/utils/download.py`: `ModelID` enum + `ModelDownloader.register(ModelSpec(...))` entries (url, files, sha256, save_dir under `models_base_dir` = `<user data dir>/models`). Engines call `ModelDownloader.get(ModelID.X)` / `.get_file_path(...)` / `.primary_path(...)` at `initialize()` time — downloads happen lazily on first use, not at startup (except whatever's in `mandatory_models`). When adding a model, register it here with a sha256 pin rather than downloading ad hoc.

### TextBlock — the shared unit of work

`modules/utils/textblock.py`'s `TextBlock` flows through the entire pipeline: detection produces `xyxy`/`bubble_xyxy`/`text_class` (`"text_bubble"` vs `"text_free"`), OCR fills `.text`, translation fills `.translation`, rendering reads both. `text_class` is the switch used throughout for bubble-specific behavior (e.g. per-type font selection in `modules/rendering/render.py`'s `font_family_for_block`, bubble-clipped inpainting masks in `modules/utils/image_utils.py`).

### Settings

`app/ui/settings/settings_page.py` (`SettingsPage`) is the single source of truth for all user-configurable state, backed by `QSettings("ComicLabs", "ComicTranslate")`. It composes per-tab widget classes from `app/ui/settings/*_page.py` (tools, credentials, LLMs, glossary, text rendering, project, export, shortcuts, account, about) via `SettingsPageUI` (`settings_ui.py`), which also owns the canonical lists of translator/OCR/detector/inpainter names and the localized-label ↔ internal-name `value_mappings`/`reverse_mappings`. Settings autosave ~1.5s after any change (debounced `QTimer` wired in `SettingsPage.__init__`) in addition to the save-on-close in `controller.py`'s `closeEvent`.

Glossary (`modules/utils/glossary.py`'s `GlossaryManager`) and translation prompts (`modules/utils/prompts.py`'s `PromptManager`) are separate JSON-file-backed stores (under the user data dir, not QSettings) with their own profile/preset systems — glossary is per-series-profile, prompts are per-style-preset (Manga/Manhwa/Webtoon/Comic/custom). Both are injected into the LLM system/user prompt via `SettingsPage.get_extra_context(...)` and `BaseLLMTranslation.get_system_prompt(...)` respectively, and both participate in translation cache keys (`pipeline/cache_manager.py`) so switching profile/preset invalidates stale cached translations. Every call site that runs an LLM translation has to build its `extra_context` through `get_extra_context(source_text)`, never `get_llm_settings()["extra_context"]` (the latter is only the plain context text box, with no glossary appended) — the multi-page branch of `ManualWorkflowController.translate_image` (`app/controllers/manual_workflow.py`, selecting several pages in the sidebar and clicking Translate) did exactly that and silently never sent the glossary.

A term's identity is `glossary.py`'s `term_key(source)` — NFC-normalised, stripped of zero-width and bidi marks, whitespace collapsed, case-folded — never the raw string. This is what `find`/`upsert`/`remove`/`keys` and `build_prompt`'s `match_only` filter all compare. Korean is why: Hangul has a composed and a decomposed encoding that render identically and compare unequal, so a raw-string glossary stores the same name twice and then fails to match either against OCR text using the other form. `deduplicate()` collapses a glossary saved before this existed (the "Merge Duplicates" button).

Which terms reach the prompt is `GlossaryManager.match_report`/`find_matches`, and it is where "the translation ignored my glossary" usually starts: measured on real OCR shapes, the old plain-substring match_only never *sent* the term. The rules, each pinned by `tests/test_glossary_matching.py`:

- **Hangul/CJK/kana/Thai terms match with every space removed** (`compact_key`) — PaddleOCR joins a wrapped name's lines with a space, and a title loses its space. Latin terms keep spaces and need **whole words** ("ice" is not in "notice"; Hangul next to a Latin term is not a word character, so "HP를" contains "HP").
- **Longest exact term first, and it claims its text.** "철수" inside "김철수" is *suppressed*, not sent — two instructions for one name contradict each other when their targets differ. It is still sent where it stands alone.
- **Fuzzy: one wrong, missing or extra letter**, only for terms with no exact match, only ≥3 letters (≥5 for Latin), never over text an exact match claimed ("박철수" must not become "김철수" when "철수" is known), never across punctuation or a space the term does not have ("김철 부장"), and not when the only difference is a Korean particle in the last place ("그림을" is 그림 + 을, not a misread "그림자"). A fuzzy line in the prompt names the spelling it was found as. Deletion windows need ≥4 letters: a 3-letter term minus one is a 2-letter word.
- `collect_source_text` joins blocks with `BLOCK_BREAK` (U+2029), which the matcher treats as a wall, so a term is never spliced from two bubbles.

After an LLM translation, `Translator.check_glossary` runs `check_translation` (exact matches only, target compared letters-only and case-folded, so Thai spacing and romanisation hyphens don't count) on the blocks as they finally stand — after a cache hit too. It is **warn-only** by the owner's choice: manual Translate shows `Messages.show_glossary_issues`, batch and webtoon batch emit `glossary_issues_found` into the Batch Report's "Glossary Warnings" section. Traditional translators are never checked — they are never sent the glossary. The LLM user prompt (`llm/base.py`'s `build_user_prompt`) puts the context/glossary *after* "sound natural", right before the text, so the glossary is the last instruction read. The Glossary page marks conflicting overlaps with a red ⚠ (`find_overlaps`), and "Test Matching" shows, for pasted OCR text, what is sent, fuzzily matched or suppressed, plus the exact prompt block.

Glossary extraction has three entry points, all landing in `modules/utils/glossary_extractor.py`: the whole OCR log on demand, the current page on demand, and — with `auto_extract` on — each page as `OCRProcessor._log_ocr_texts` finishes it. That last one crosses a thread boundary, so it goes through `GlossaryPage.page_text_recognized` (a Qt signal, queued onto the GUI thread).

Two things govern how text reaches the model, and both exist for the same reason — a model given a handful of lines cannot tell a recurring character from a one-off shout:

- `extract_glossary_terms` **chunks rather than truncates**. `split_into_chunks` cuts at `CHUNK_LIMIT` (15k chars) on line boundaries and every chunk is sent. A `seen` set of `term_key`s spans the whole run: it seeds from the existing glossary, is fed back into each chunk's "do NOT repeat" list, and filters results — which is also what stops a model repeating itself *within* one response from producing duplicate entries. A chunk that fails is logged and skipped, never fatal.
- `GlossaryPage` **buffers pages** instead of extracting per page: `_queue_page` accumulates until `PAGE_BATCH_CHARS`, with `_page_flush_timer` (`PAGE_FLUSH_IDLE_MS`) catching the tail of a batch that stopped arriving. Explicit "Extract from This Page" passes `flush_now=True`. Only one extraction runs at a time — it is an LLM call, and one per page in parallel would rate-limit the account immediately.

`modules/utils/workspaces.py`'s `WorkspaceManager` is a third store of the same shape (one JSON per workspace under `<user data>/workspaces/`, plus a `config.json` naming the active one). A workspace bundles the per-series choices that otherwise have to be changed in four places at once: source folders, glossary profile, prompt preset, and language pair. `controller.py`'s `apply_workspace`/`capture_workspace_state` are the only places that read/write those UI widgets from a workspace; the picker lives at the top of the file tree panel.

### Pages sidebar

`app/ui/list_view.py`'s `PageListView` is the flat page strip and stays the ordering model — row index is the index into `main.image_files`. `app/ui/file_tree_panel.py`'s `FileTreePanel` shows the same pages grouped by source folder and is a pure view: `ImageController.refresh_file_tree()` rebuilds it from `image_files`/`image_states` and it does nothing while hidden. Its actions emit **file paths**; the flat list still emits base names, so every handler routes through `ImageController.resolve_page_paths()` (exact path wins, base name is the fallback) — two chapters of a series routinely share `002.png`.

Reopening a saved project materializes each page into its own `<temp>/unique_images/<id>/` directory, so a page's working path says nothing about the series layout. Both project loaders populate `main.path_originals` (working path → original path) and the tree groups and labels by that, while every path it emits stays the working one.

### Editor canvas

`app/ui/canvas/image_viewer.py`'s `ImageViewer` (a `QGraphicsView`) is the editing surface. Scene items are typed by role: `self.photo` (the artwork), `MoveableRectItem` (detection boxes), `TextBlockItem` (rendered translation text), `QGraphicsPathItem` (segmentation/brush strokes), and `QGraphicsPixmapItem` with `.setData(0, hash)` (inpaint patches, added via `app/ui/commands/base.py`'s `PatchCommandBase`). All of them are added to the scene as **top-level items with no parent**; nothing is a child of `self.photo`. `app/ui/canvas/scene_registry.py`'s `kind_of(item)` is the one place that decides which of those an item is — ask it instead of repeating the class checks.

Every editable object carries a stable `object_id` (`modules/utils/common_utils.new_object_id`): an attribute on text items and boxes, data slot 1 on strokes and patches, a field on `TextBlock`, and a key in every serialised state dict. It survives undo/redo, project save/load and webtoon page split/merge (every fragment of a page-spanning object keeps the one id). Patches keep their content `hash` too, as the dedup key — two identities, not to be conflated.

**Never call `parentItem()` on a parentless item.** In PySide6 (seen on 6.11.2) that hands ownership of the C++ item to its Python wrapper, and the item is deleted from the scene the next time that wrapper is garbage-collected. Strokes from `scene.addPath` and patch pixmaps usually have no other live wrapper, so they silently vanish. Use `scene_registry.is_top_level(item)` (`topLevelItem() is item`). This deleted webtoon strokes whenever a page loaded at a different height than estimated.

### Layers

A page is five fixed groups, bottom to top: Raw Image, Inpaint Patches, Brush Strokes, Boxes, Editable Text (`core/layers.py`, Qt-free). Every object inside is its own layer with visible / locked / opacity / name / order. Layers are document-level but storage stays per page — there is no document-owned model:

- **Object props** live under one optional `"layer"` key on the object's own state dict and on the scene item (data slot 2, via `scene_registry.get_item_layer`/`set_item_layer`/`put_layer`). The key is written only when it differs from the default, so an untouched project serialises byte-identically. Any code that rebuilds an object's dict field by field (the webtoon managers, undo snapshots, patch dicts) has to carry `layer` alongside `object_id`.
- **Group props** are `main.document_layers` (`DocumentLayers`), saved in the v2 manifest; `effective()` combines them (visible AND, locked OR, opacity multiplied).
- **Applying them:** `app/ui/canvas/layer_apply.py`'s `apply_layer_state`, run over every page item by `ImageViewer.refresh_layers()`. That is hooked to every undo-group index/active-stack change (which covers every command), page loads and webtoon page loads — so no item-creation site applies layers itself. Locked items accept no mouse buttons; the click hit test (`EventHandler._item_at`) and the eraser skip locked and hidden items.
- **Changing them:** only through `main.layer_ctrl` (`app/controllers/layers.py`). Object edits are undoable (`app/ui/commands/layers.py`) and land on the live item *and* every stored copy — patches persist through `image_patches`, not scene serialisation. Group toggles are view state: saved, not undo steps.
- **The panel** (`app/ui/layers_panel.py`) holds no state and rebuilds from the scene; in webtoon mode it lists the loaded pages' objects only.
- **Processing ignores visibility**: `get_image_array(include_patches=True)` paints patches directly, so hiding a layer never changes OCR/translation/inpaint input. Batch re-runs keep locked text (`merge_preserving_locked`).
- **Export:** flattened outputs (`save_renderer.ImageSaveRenderer`, which also makes the PSD's flattened preview) skip hidden objects and apply opacity; the PSD writes hidden objects/groups as *hidden layers* with their opacity, names and order. PhotoshopAPI layer `name` is read-only after construction.

### Canvas tools

`viewer.current_tool` is a string (`box`, `brush`, `eraser`, `pan`, `paint`, `restore`, `eyedropper`, `marquee`, `balloon`, `wand`, `lasso`), set by `set_tool` and dispatched in `event_handler.py`. Buttons register themselves in `self.tool_buttons[name]` in `builders/workspace.py`, which is what makes them mutually exclusive — nothing else needs touching to add one. The options bar follows the tool (`refresh_options_bar`) and has a horizontal `Ignored` size policy: a bar wider than the canvas column once widened the whole window past the screen.

The wand, the balloon tool and the lasso end at `drawing_manager.commit_region(path, modifiers)`, which sends the region where the options bar's **Pick into** switch says: into the canvas selection (default), or — `region_output = "mask"` — to `add_region_stroke(path)`, the red stroke the Clean step inpaints, exactly as before selections existed.

**The canvas selection** (`app/ui/canvas/selection.py`, maths Qt-free in `core/selection.py`) is marching ants, not a stroke, a layer or anything saved. It is a `QPainterPath` in **scene** coordinates, because in webtoon mode a consumer's image is only the loaded slice and which slice that is changes with scrolling; each consumer rasterises it into its own image space (`rasterise`, `alpha`). Combining (plain = replace, Shift add, Alt subtract, both intersect; the lasso reads modifiers when an outline *starts*) and refining (grow/shrink/smooth) go through pixels over the path's bounding box and back through `mask_to_polygons`; `rasterise_path` fills *and* strokes 1 px, because contours run through boundary-pixel centres and a plain fill drops the right/bottom edge — without it every refine shrank the selection (`test_mask_to_path_to_mask_is_exact`). Everything is clipped to `page_area()` (the page, or the loaded webtoon slice), so Select All/Invert never build a strip-sized array. Every change is a `SelectionCommand` on the undo stack; page loads call `forget()` from `clear_scene`. The overlay (`SelectionOverlay`) is deliberately **not** a `QGraphicsPathItem` — dozens of `isinstance(item, QGraphicsPathItem)` checks treat those as mask strokes — and has an empty `shape()`, so it is never hit by a click; the marquee's rubber band is the same item. Feather is applied by consumers: `alpha()` extends the hard mask with its *edge values* before feathering, since the page edge is not an outline (padding with empty faded every selection at the border).

**The balloon tool** (`flood_select.balloon_select`, Qt-free; `drawing_manager.balloon_at`) selects a bubble's inside with its lettering (holes filled) and never its outline — unlike the wand it does not grow the region, since the anti-aliased rim belongs to the outline. It is bounded by the smallest detected `bubble_xyxy` around the click (padded 4 px; webtoon blocks mapped through `filter_and_convert_visible_blocks` and restored), which the bubble-seg detector already tightened to its instance masks, so a gap in the outline cannot pour it into the panel. With no detection, a region that touches the page edge or covers over 25% of the page is refused as a leak (at 40% a light screentone panel passed as a bubble), and a seed whose darkest channel is under 180 as not a bubble; `viewer.balloon_refused` carries the reason and the controller says why in a toast — it never selects the page. The options bar's **Modify ▾** menu (grow, shrink, smooth, feather) asks for pixels and calls `selection.refine`, one undo step each; it is a menu so the bar stays within the canvas width. When lupdate reads this code: never alias `QCoreApplication.translate` to `tr` (it files `tr("Context", "text")` as the source "Context" in a nameless context), and a `#:` comment above a string is a translator note that leaks into the catalogue.

**Clean Selection** (`app/controllers/selection.py` → `InpaintingHandler.inpaint_selection`; also what the Clean step does when nothing but a selection is marked) reads image, alpha and webtoon mappings on the GUI thread, then `core.selection.plan_clean` decides what to touch. The wand fills a bubble's lettering holes on purpose, so a clicked bubble is its whole white: inpainting all of it made AOT invent the bubble from its outline, a grey smear. When the 6 px band just inside the selection's edge is mostly one colour — the background is read there, not from the whole selection, whose majority is the lettering itself in a snug marquee around a bold SFX — only pixels that differ from it are cleaned — painted in that colour if the background is even (no model, ~0.3 s), else inpainted — and components touching the selection's boundary are skipped, because the wand's 2 px growth puts a sliver of the bubble's *outline* inside the selection and painting it thinned the line. Artwork with no dominant colour is inpainted whole. The result is tidied (`_denoise_cleaned`) *before* being mixed back by the alpha, and patches are cut with `denoise=False`: the tidy-up smooths a ring around its mask, and outside the selection is exactly where nothing may change. Mask strokes are left alone. Shortcuts: Ctrl+A / Ctrl+Shift+A / Ctrl+Shift+I (Ctrl+D was already the brush toggle); they do nothing while a text field or a canvas text box is being typed in.

**Pixel tools** — the paint brush, the restore eraser (brushes the raw page back, undoing cleaning where it passes) and the eyedropper (also Alt+click while painting) — never touch the raw image either: a stroke is a `pixel_session.PixelSession` that reads the composite, its source (a flat colour or `get_image_array(include_patches=False)`), the selection as alpha and the webtoon slice offset on the press, stamps dabs into a float coverage map (`core/paint.py`, Qt-free: `c += (1 − c)·dab·flow`, opacity applied once as a ceiling), and on release hands `PaintController` a `PixelEdit` (blended image + changed-pixel mask) that goes through the same seam as Clean Selection — `get_inpainted_patches(..., denoise=False)` → `apply_patch_list`, one undo macro, nothing pushed if no pixel changed. The preview is a plain `QGraphicsItem` holding a QImage over the touched rect (a pixmap item would read as the Raw Image layer), removed on release, on `set_tool` and on `clear_scene`. Pen pressure: `handle_viewport_event` records `QTabletEvent.pressure()` on `viewer.tablet_pressure` and leaves the event unaccepted, so Qt still synthesises the mouse events every tool handles; the options bar's Pen pressure checkboxes scale size and/or flow. Size is the brush slider's, in image pixels like the mask brush's pen; colour, hardness, opacity and the pressure options persist under `paint/`. Writing the restore eraser uncovered a real compositing bug: `get_image_array` walked `scene.items()`, which lists the *topmost* item first, so overlapping patches composed in reverse — the screen showed the newer patch while OCR, inpainting and the pixel tools read the older one. Both it and the webtoon composite now iterate `items(Qt.SortOrder.AscendingOrder)` (`tests/test_patch_compositing.py`).

The magic wand (`modules/utils/flood_select.py`, kept Qt-free so it can be tested as array maths) grows a region from the clicked pixel and hands back a mask. `drawing_manager.flood_fill_at` turns that into **an ordinary filled `QGraphicsPathItem` with a `BrushStrokeCommand`** — deliberately the same thing the brush produces, so mask generation, undo and project saving needed no changes at all.

Two decisions there are load-bearing and non-obvious:

- **Holes are closed in the mask, not by the path's fill rule.** `imk.find_contours` winds an enclosed gap opposite to its outer contour, so `WindingFill` leaves it empty. Clicking a bubble would then mask a ring *around* the lettering — the opposite of what cleaning it needs.
- **Only holes smaller than the region enclosing them are filled.** Every closed shape encloses something, so unbounded filling makes clicking a 4px bubble border select the whole bubble, and clicking a panel border select the whole panel.

The lasso is one tool told apart by what the mouse does: drag past `LASSO_DRAG_THRESHOLD` traces a loop freehand and commits on release, while clicks below it accumulate polygon vertices closed by double-click, Enter, or abandoned with Escape. The in-progress outline is a real scene item, so `has_drawn_elements` and `generate_mask_from_strokes` both skip `lasso_preview` explicitly — without that, an outline the user never finished still gets inpainted. `set_tool` cancels an unfinished outline when the user reaches for something else, and the viewer takes focus while the lasso is active so Enter and Escape reach `keyPressEvent` at all.

`get_image_array(include_patches=True)` always composes patches for OCR/translation/inpainting regardless of display state.

Undo/redo for canvas edits goes through `QUndoCommand` subclasses in `app/ui/commands/` pushed onto `controller.py`'s `QUndoStack`.

`app/ui/canvas/handles.py` owns the eight resize handles drawn on a selected `MoveableRectItem` or `TextBlockItem`. Both the drawn square and the (larger) grab area are sized in **screen** pixels and divided by `item_view_scale(item)`, so they stay the same size to the hand at any zoom — a fixed image-space margin is 5px at 25% zoom, which is exactly when boxes get dragged around. `paint_handles` draws them *inset* rather than centred on the border: they must stay inside `boundingRect()`, since that is the only region Qt repaints, and several call sites use `boundingRect()` for resize math and transform origins so it cannot be widened.

### Text effects: gradient fill and curved text

Both live on `TextBlockItem` (`app/ui/canvas/text_item.py`) next to the drop shadow, with the geometry split out Qt-free into `modules/rendering/text_effects.py` (`gradient_line`, `arc_placements`, `arc_bulge`). Adding either meant touching the same seven places the shadow already occupies: the item, `text/text_item_properties.py` (save/load), `image_viewer.py` and `save_renderer.py` (apply on create), `builders/workspace.py` (toolbar), `controllers/text.py` (widgets → item, item → widgets, plus `widgets_to_block`) and `controller.py` (signals).

- **The gradient is a document-wide char-format brush in `LogicalMode`, sized from `document().size()`.** Qt's `ObjectBoundingMode` anchors a text brush to each *glyph run*, so a two-line block gets the identical sweep twice instead of one across the whole thing. Because the axis is tied to the laid-out document, `_on_text_changed` has to rebuild it — and since merging a char format is itself a document edit, `_applying_gradient` guards the recursion. It is item-wide by design and replaces per-range colours while on.
- **Curved text paints outside its box, so `boundingRect()` grows and `text_rect()` does not.** `text_rect()` (the plain document rect) is what handles, resize math, `TextBlockState` and the saved width/height use; `boundingRect()` adds the arc's bulge symmetrically, purely so Qt repaints enough — symmetric because the transform origin and rotation pivot are its centre. Anything reading `boundingRect()` for *geometry* rather than for repaint is a bug.
- **Curved glyphs are baked into paths in item coordinates, never drawn under a rotated painter.** Rotating the painter per glyph and calling `drawText` looks equivalent and is not: a gradient brush resolves against the painter's current transform, so every letter samples the gradient at its own origin and the whole word comes out one flat colour. The strokes come from the union of the glyph paths instead of 16 displaced copies. Each character is read run by run from the document (`_curved_characters`: the fragment's own font, size and solid brush, resolved over `document().defaultFont()`), so a coloured or enlarged range keeps its format when bent; a fragment whose brush is a gradient falls back to `fill_brush()`. Never size the curve from the item's `font_size` copy — it is a step apart from the document mid-resize, and reading it makes bending the text resize it.

**Stroke layers** (`stroke_layers`, `core/text_style.StrokeLayer`) stack item-wide strokes outside the outline, innermost first; layer *n* reaches outline width + the widths of layers 1..*n*. `effective_outlines()` expresses them as extra whole-document outlines at those reaches, which is all Skia (`spec_for_item`, widest first) and the curve need. The flat Qt path does **not** draw them with the outline's 16-offset trick — that only covers the ring at exactly the offset radius and leaves visible gaps at stacked widths — but strokes `document_glyph_path()` (every glyph from each block's `layout().glyphRuns()`) with a real pen, then runs the outline pass for `selection_outlines` over it; the vertical layout places its glyphs outside the block layouts, so it falls back to the offset trick. `boundingRect()` grows by `stroke_reach()` (repaint only, symmetric; `text_rect()` unchanged) because the item is device-cached to that rect and would otherwise clip the outer ring. Saved as one optional `stroke_layers` key, omitted when empty. The shadow's opacity is the alpha of `shadow_color`, set by its own control — the colour button alone holds an opaque colour.

**Perspective** (`quad`) is four corners as *fractions* of the text box (TL, TR, BR, BL; `modules/rendering/text_effects.normalise_quad`, identity → None), so resizing the box keeps the distortion's shape. `apply_quad()` turns it into the item's own `setTransform(QTransform.quadToQuad(...))` and re-runs whenever the box changes (`setTextWidth` override, `_on_text_changed`, `apply_effects` after undo, the vertical layout's size signal); rotation and scale stay item properties on top. A folded or self-crossing quad is refused (`quad_is_convex`) — Qt happily maps it and draws the text inside out. The toolbar's **Perspective** toggle sets the class-level `TextBlockItem.perspective_editing`: then `resize_item` becomes `drag_perspective`, a corner handle moves its corner and an edge handle moves its two corners together (skew), in the box's post-perspective coordinates (`transform().map(mapFromScene(p))`). A perspective drag changes no geometry `TextBlockState` sees, so the event handler records it as one `TextFormatCommand` instead of `change_undo`. Handles on a non-affine item are drawn by `handles.paint_handles_projected` as screen-aligned squares; drawn in item coordinates they would be warped with the text. Skia's raster goes through the painter's projective transform and matches Qt to a pixel; the PSD's cached type raster is rendered through the item, so it carries the perspective while the text stays editable.

**Warp** has six styles in one dropdown beside the bend amount. **Arc** is still `curvature` (glyphs placed along a circle, above). The other five — `modules/rendering/text_effects.WARP_STYLES`: arch, bulge, flag, wave, rise — are *point* warps: `warp_offset(style, bend, u, v)` shifts each point of each glyph outline vertically (never horizontally, which would crush letters into their neighbours) by a fraction of `warp_scale()` — the box height, or 30% of its width when larger, or a bend on a one-line caption barely shows. `document_glyph_runs()` reads the glyphs per format run from the block layouts (`glyphRuns(from, length)` per fragment), so per-range fonts and colours survive; `_warp_path` flattens each outline and subdivides every edge before mapping, or straight stems stay straight chords. Strokes come from the warped union, like the curve. A warped item paints on the Qt path under either engine (no Skia equivalent), except while editing, where Qt's flat paint draws the caret. `boundingRect()` grows by `warp_extent` (repaint only). Saved as optional `warp_style`/`warp_bend` keys.

**Style presets** (`modules/utils/text_presets.py`, Qt-free) are named looks: every `TextPreset` field is optional and `None` leaves the item's own value alone. Built-ins (Speech, Shout, Thought, Narration, SFX) are read-only and stored by their English name — that is the key a setting refers to — while combos show `preset_label(name)`, translated; a user style may not take a built-in's name or its translation; the user's own live in `<user data>/text_presets.json` (unknown keys survive a save, in `extra`). One mechanism serves two uses. The toolbar's Style row applies *every* field a preset holds to the selected text items (`text_ctrl.apply_style_preset`, one undo macro of `TextFormatCommand`s); "Save…" captures the item (`app/ui/canvas/text/presets.preset_from_item`) **without its size**, since rendered text is fitted to its bubble. `Settings > Text Rendering > Default Text Style` picks a preset per text class for *newly rendered* text, and that applies only `LOOK_FIELDS` — colour, outline, strokes, shadow, gradient, warp, curve — never font, size, weight or spacing, because the renderer already fitted the text in its own font and any of those would overflow the box. The pipeline side is `apply_to_state` over a `build_text_item_state` dict (batch and webtoon batch, via `render.default_preset_for`); the manual Render side is `on_blk_rendered`. `TextRenderingSettings.default_presets` holds preset objects, so `save_main_page_settings` drops it before walking the dataclass into QSettings and persists the chosen *names* (`default_preset_bubble`/`default_preset_free`) instead — walking it once made closing the window raise.

### Theme (Toon Studio)

Every UI colour comes from `core/theme_tokens.py` (Qt-free): two palettes, `DARK` and `LIGHT`, with the same keys (ground < panel < raised < hover surfaces, lines, `text_1..3`, one `accent`, `on_accent`, status colours). The dayu `MTheme` maps them onto its own names in `_apply_tokens` (`background_color` = panel, `background_in_color` = raised, …) and substitutes them into `resources/static/main.qss`; `dayu_theme.tokens` is the current table and `dayu_theme.is_dark` the mode. Hand-styled widgets (home screen, title bar, search panel, batch report) read `theme_tokens.palette(dark=…)` in their `apply_theme`, which `ComicTranslateUI.apply_theme` calls on every switch — never a hex literal; `tests/test_theme_tokens.py` rejects the old accent blues and any hex in the files already converted, and checks every text/background pair in `CONTRAST_RULES` in both modes.

Two traps. **Text on the accent is `on_accent` (dark ink in dark mode), never white** — white on the dark-mode pink is 3:1. Qt's stylesheet `selection-color` puts that ink into the palette's `highlightedText`, so a delegate that paints a *tinted* selection (the page strip) must draw ordinary text colour, not `highlightedText`, or the text vanishes (1.8:1 — caught in a screenshot, pinned by `test_the_selected_page_row_keeps_its_text_readable`). Icons are the Toon Studio line set, generated from one table by `scripts/build_icons.py` into `resources/static/` under the file names the code already uses (24 grid, 1.75 stroke). **Every themed icon must draw in `#555555`**: that is the literal `MIcon` replaces with the theme, hover or accent colour; three old icons did not, so the Type tool rendered black on the dark theme. `tests/test_icons.py` checks that every `.svg` the code names exists and carries that colour (a short allow-list covers fixed-colour images such as the stylesheet's checkbox marks), and that the files match the table (`--check`). Tool buttons: hover = raised fill and body-text icon, checked = accent tint and accent icon — hover never borrows the accent, so it cannot look selected.

The UI face, IBM Plex Sans Thai (OFL, `resources/fonts/ui/`), is registered by `app/ui/fonts.load_ui_fonts()` right after the QApplication exists; the theme's `font_family` lists it first and falls back to platform faces if it did not load.

### Stitch page (joining webtoon slices)

Raw webtoon chapters arrive as dozens of slices cut wherever the uploader cut them, often through a bubble — which then reaches detection and OCR as two halves on two pages. The Stitch page (nav rail, between Home and Settings) stacks the slices and re-cuts the strip into pages of about a target height at rows with no artwork. The maths is Qt-free in `modules/utils/stitch.py` (so `check_headless.py` gates it); `app/ui/stitch_page.py` is the page around it.

- **A row is empty when neighbouring pixels barely differ across it**: `row_busyness` is the largest jump between horizontally adjacent grey pixels (SmartStitch's detector), so a flat white, black or tinted gutter scores ~0. Scores are computed per slice and concatenated — the strip is never materialised just to decide where to cut; `assemble` builds each page from row ranges of the source slices.
- **`find_cuts` scans up from the target, then down a quarter page**, never closer than half a page to the previous cut, and places the cut nearest the target inside that quiet run but `GUTTER_INSET` rows off its ends (so pages don't end flush against a panel, and a wide blank stretch doesn't shrink a page). No quiet row → a cut at the target, reported as *forced* and drawn in the warn colour. A tail under a quarter page merges into the page before it.
- **Project pages count as they stand in the editor**: `StitchPage._resolve` looks up `image_data`/`image_history` on the GUI thread and hands the worker an array or a path — the worker never touches `main`. Jobs go through `main.run_threaded`; progress crosses back via the page's own signal.
- "Open as New Project" calls `_guarded_thread_load_images`; `ImageController` switches to the editor from the Stitch page as it does from the home screen. Settings persist under a `stitch/` group in the usual `QSettings`.

### Name and storage identity

What users see is **Toon Studio**: the window title (`theme_tokens.BRAND_NAME`), the splash, the app icon and the built executable (`--name ToonStudio` in every build workflow). The bubble mark, `icon.ico`/`.icns`/`.png` and `splash.png` in `resources/icons/` are all rendered by `scripts/build_brand.py` from one drawing — regenerate, never hand-edit. **What stores data keeps its old name on purpose**, because renaming it silently resets every existing user: `QSettings("ComicLabs", "ComicTranslate")`, `get_user_data_dir("ComicTranslate")` (glossaries, prompts, workspaces, models), the `.ctpr` extension, the single-instance server name and the Windows AppUserModelID. `tests/test_brand.py` pins them. The account strings ("Sign in to Comic Translate") also stay: they name the hosted service, which is still Comic Translate's.

### Caching

`pipeline/cache_manager.py`'s `CacheManager` caches OCR and translation results keyed by `(image_hash, model/translator_key, lang(s), device, ...extra)` — extra key components include the glossary/prompt fingerprint and `extra_context` hash, so results are invalidated exactly when something that could change them changes. Batch processing checks this cache before re-running OCR/translation (see `pipeline/batch_processor.py`'s `_apply_cached_ocr`).

### Webtoon (long-strip) mode

Long vertical-strip images are handled separately throughout: `app/ui/canvas/webtoons/` (viewer/scene management for lazy-loaded tall strips) and `pipeline/webtoon_batch/` (chunked batch detect/OCR/inpaint/render with seam-aware stitching so text isn't cut at chunk boundaries — see `chunk.py`'s stitched-context detection and `_shift_block_vertical`).

### Localization (UI language)

Catalogues live in `resources/translations/ct_<lang>.ts`, compiled to `compiled/ct_<lang>.qm` and loaded by `comic.py`'s `load_translation`. Adding a language means: a `ct_<lang>.ts`, its compiled `.qm`, an entry in `load_translation`'s display-name → code dict and `get_system_language`'s code → display-name dict, plus the display name in `SettingsPageUI.languages` and `value_mappings` (`app/ui/settings/settings_ui.py`). Comic source/target language names are separately mapped back to canonical English by `ComicTranslateUI.lang_mapping` (`app/ui/main_window/window.py`), so translating them is safe — but two languages must never translate to the same string or the dict collapses.

Always build the `.qm` through `scripts/build_translations.py`, not `lrelease`. PySide6 looks a string up under each class name in the object's MRO (so a string written in a mixin or base class is found from a subclass), but `lupdate` names a context after the expression at the call site — `self.main.tr(...)` is filed under the literal context `"self.main"`, which is not a class name and never matches. That silently strands ~60 strings in every language. The script appends a catch-all `@fallback` context to a temporary copy of the `.ts` — the committed `.ts` stays exactly as lupdate writes it — and `ContextFallbackTranslator` consults it when the real contexts miss. Per-context entries still win, so a word translated differently depending on where it appears keeps its specific translation.

A `QTranslator` subclass must return `None`, never `""`, for a miss. An empty string is a valid translation to Qt: it blanks the widget out *and* stops PySide6 walking up the MRO to the class that actually holds the string.

### Language/direction handling

`modules/utils/language_utils.py` centralizes language code mapping, RTL detection (Arabic/Hebrew/Persian), and no-space-language detection (`zh`/`ja`/`th` — affects both LLM text preprocessing and `modules/rendering/render.py`'s word-wrap algorithm, which has a dedicated Thai-aware path using cluster-safe breaks and optional `pythainlp` word segmentation, separate from the CJK "one character per line" fallback). Vertical text layout (CJK) is handled by `app/ui/canvas/text/vertical_layout.py`'s `VerticalTextDocumentLayout`.
